# Éditeur OSMrides (local, Docker)

Éditeur WYSIWYG des données **du jeu** d'une attraction (lot 1 : barrières de file et salle de contrôle ; issue #22 : zone d'attente du quai d'embarquement ; issue #27 : profondeur des travées d'attente ; lot 3 : paramètres de l'attraction). Il ouvre la vraie page `jeu.html` (bac à sable, simulation figée) et ajoute une couche d'édition par-dessus : ce qui est affiché est exactement le rendu du jeu. Il écrit `lieux/<type>/<lieu>/<el>.game.js` (et, sur demande, `lieu.js` et les données OSM `<el>.data.js` : « Réimporter depuis OSM »). Décisions : `docs/ARCHITECTURE.md` (D1 à D9).

L'éditeur se lance **depuis un dépôt de jeu** (`osmrides_parks`, `osmrides_skiresort`) : il sert `editor/` et `engine/` de sa version d'osmrides, `jeu.html` et `lieux/` du dépôt de jeu (`docs/versions.md`). Le jeu publié n'a besoin ni de l'éditeur ni de Docker.

## Démarrer / arrêter

Dans le dépôt de jeu, avec `compose.yaml` copié depuis `tools/jeu/compose.yaml` :

```sh
export T2Z_UID=$(id -u) T2Z_GID=$(id -g)   # les fichiers écrits appartiendront à votre utilisateur (défaut 1000:1000)
docker compose up -d                        # image node:22-alpine ; télécharge l'éditeur de la version écrite dans jeu.html
# ouvrir http://127.0.0.1:8787/  (redirige vers /editor/?site=…)
docker compose logs -f                      # chaque écriture est journalisée
docker compose down
```

Sans Docker (Node 22, aucune dépendance) : `sh ../osmrides/tools/editeur.sh 0.0.1` depuis le dépôt de jeu, ou `T2Z_ROOT=../osmrides_parks node editor/server.js` depuis ce dépôt (éditeur en cours de développement ; `PORT`, `HOST`, `OSM_CONFIG` facultatifs). Tous les `lieux/<type>/<lieu>/<el>` du dépôt de jeu sont proposés (`?site=parc/asterix/zeus`).

## Utilisation

- Choisir l'attraction en haut. La carte se déplace et se zoome comme dans le jeu.
- **Barrières** (issue #37 : posées à la main, aucune barrière calculée ; liste à droite ; sur la carte : cyan = fermée au début de la partie, orange = ouverte ; point gris = ancienne barrière convertie ; trait plein = fermée, tirets = ouverte) : **Ajouter une barrière** (bouton, puis clic sur l'allée : poteau sur la bordure côté clic, vantail en travers) ; glisser pour déplacer, poignée A pour tourner et régler la longueur ; clic simple (ou choix dans la liste) : fenêtre modale « Ouverte au début de la partie », « Inverser le sens d'ouverture », **Supprimer la barrière** (clé retirée). Dans le jeu, chacune s'ouvre et se ferme seule au clic.
- **Salle de contrôle** (une seule par attraction, celle du pupitre) : sans `game.js`, le jeu prend `SITE.booth` ; l'éditeur propose de la reprendre (bouton « Reprendre la salle », ou automatiquement à la première modification). Glisser = déplacer, coins = redimensionner, rond = tourner (côté vitre vers la voie). Supprimer / créer (seulement s'il n'y en a pas).
- **Zone d'attente du quai** (section « Zone d'attente du quai », ou clic dans la zone sur la carte) : polygone entre la fin de la file et les portillons, où les visiteurs attendent juste derrière les portillons. Sans `game.js`, la zone calculée par le jeu est dessinée **en tirets** (travées et couloir d'attente) ; la première modification la reprend dans `game.js` (trait plein). Zone sélectionnée : glisser un **sommet** (carré) pour le déplacer, glisser ou cliquer un **rond** (milieu d'un bord) pour ajouter un sommet, glisser l'intérieur pour tout déplacer ; un sommet sélectionné se règle aussi au clavier (x, z) et se retire par **Supprimer le sommet** (3 sommets au moins). **Revenir au calcul auto** retire la zone de `game.js`. Les places d'attente sont recalculées en direct : deux par portillon, premier rang collé au portillon, puis une **réserve** en rangs successifs dans tout le polygone (la zone se remplit quand les places des portillons sont prises ; on avance à une place libérée), jamais hors du polygone. **Fin de la file** (toujours affichée, trait vert épais) : dernière portion du trajet des visiteurs vers le quai (fin du dernier tronçon de file puis `SITE.board.via`), **losange vert plein cerclé** = point où ils entrent dans la zone, losanges creux = bords de l'allée au bout de la file. **Aimant** : un sommet glissé (ou créé par un rond) se colle exactement au point de fin de file à moins de 11 px écran (sinon à un bord de l'allée) ; maintenir **Alt** pour le poser librement. Le polygone doit toucher la fin de la file ; les garde-corps de file qu'il recouvre disparaissent au rechargement du jeu.
- **Profondeur des travées d'attente** (section « Zone d'attente du quai », issue #27) : distance de la ligne des portillons au bout des séparateurs, en m. Valeur calculée par le jeu affichée par défaut (trait orange en tirets sur la carte) ; saisir une valeur ou glisser la **poignée** (losange orange, au portillon du milieu) la règle (`game.js`, trait plein) ; **Revenir au calcul auto** retire la clé. Le jeu en déduit le nombre de rangs (un au moins, 6 m au plus, ESTIMÉ), les séparateurs dessinés, le couloir d'attente juste derrière et le départ de la réserve ; les rangs au-delà des places des portillons servent de réserve à leur portillon (remplis quand les places du portillon sont prises). Le dégagement des allées de file le long du quai suit au rechargement du jeu.
- **Entrée de la file** (section « Entrée de la file », issue #39) : prolongement de la file depuis le début du chemin de file OSM vers la zone piétonne ou l'accès, par où arrivent les visiteurs. Calcul du jeu affiché par défaut (trait bleu en tirets, `SITE.queue.mouth` / `mouthMax` / `link`) ; poignée ronde bleue au bout à glisser, ou champs **Longueur (m)** et **Orientation (°)** (0 = est, 90 = sud) ; le jeu se recharge en cadre à chaque réglage ; longueur ramenée au bord de la surface praticable (zone piétonne, chemin OSM, hors bâtiment ; tirets fins = longueur demandée au-delà) ; **Revenir au calcul auto** retire la clé. Les barrières posées à la main ne bougent pas.
- **Aimant des barrières** (propriétaire, 20/11) : en glissant une barrière, le pivot se colle au bord le plus proche d'une allée de file (bordure dessinée : largeur OSM ou dessinée) à moins de 11 px ; en réglant la poignée A, l'angle choisi est gardé (n'importe quel angle par rapport à l'allée) et seule la longueur s'ajuste pour que le bout se colle au bord opposé, ou à un autre bord d'allée, là où il arrive ; cercle blanc = aimanté ; **Alt** maintenue = sans aimant.
- **Attraction** (section « Attraction », lot 3, D9) : règle sans code ce qui est écrit dans `SITE` : **sous-type** (bois, bobsleigh, inversé, acier ; avertissement : voie, gare et garage ne sont pas refaits), **wagons** (longueur, nombre par train, places, places côte à côte, sécurités ; longueur du train affichée, 40 m au plus), **trains** (nom, deux couleurs, usure, voie de garage au départ ; ajouter / retirer, de 1 à 8 ; le premier est à quai, chaque train garé a besoin d'une place au garage), **couleurs de la voie** (inversé / acier : poutre, rails, supports) ou **de la gouttière** (bobsleigh), **physique de base** (roulement, traînée, vitesse minimale). Chaque champ montre la valeur d'origine de `SITE` ; un champ modifié est entouré en doré ; le bouton **Origine** revient à la valeur d'origine (la surcharge est retirée de `game.js`). Chaque modification **recharge le jeu en cadre** pour montrer l'effet (le brouillon non enregistré, barrières et zones comprises, est conservé). Valeur hors bornes : erreur dans « Fichier » et refus à l'enregistrement. Si le jeu ne se charge plus (par exemple trop de trains pour le garage), le bouton « Annuler la dernière modification » apparaît. Les valeurs de `SITE` sont des réglages de jeu, souvent ESTIMÉES (couleurs de train supposées, longueur de wagon) : ne pas les présenter comme mesurées.
- **Exploitation** (section du même nom, osmrides#53, `GAME.site`, tous types) : objectif de l'attraction (`goal`), textes d'orage et de bilan excellent (`text`), zone et point favori des éclairs (`strike`), postes de maintenance (`jobsites`, « Poser au clic » puis cliquer la carte), caméras (`cams`, « Cadrage courant » prend la position et le zoom actuels de la carte, « Ajouter une caméra » ; une caméra de SITE ne se supprime pas, son cadrage revient à l'origine). Chaque réglage garde la valeur de `SITE` tant qu'on n'y touche pas (bouton « Origine ») ; aucun n'a d'équivalent OSM, donc aucun n'est envoyé vers OSM.
- **Attraction, suite** (montagnes russes, osmrides#53) : durée d'un tour (`lap`), trains en ligne (`maxRun`), arrêt en gare (`stopBack`), profondeurs des quais (`plat.load`, `exit`, `back`, `front`), largeur, places en ligne et écart des places du wagon (`car.w`, `car.inline`, `car.pitch`), **zones de freinage « Frein k » suivies d'un canton** (`zones.B<k>` : vitesse limite `trim.v`, vitesse de lancement `launch`, arrêt obligatoire `stop`, temps d'arrêt `hold` ; 0 = pas de réglage), appareil de voie (`yard.move` {v, vc, t}, `yard.devName`, `yard.devLabel`) . **Valeurs déduites** par le moteur (`dropAfter` : profil des hauteurs après le lift, `loadSide` : côté où arrive la file) : l'éditeur affiche la valeur effective et celle déduite ; n'y toucher que pour corriger un cas particulier (priorité `GAME` > `SITE` > déduction).
- **Rails mobiles** (section du même nom, osmrides#64 et #69) : pont transbordeur, rail unique ou aiguillage coulissant, un seul mécanisme de **groupes** (1 rail indépendant ou N rails verrouillés ensemble, déplacés d'un bloc ; positions communes au groupe). Clic sur un rail (contour orange) : **fenêtre modale** du groupe (Ajouter une position ici, positions, « Ajouter un rail au groupe » puis clic sur l'autre rail ou Maj + clic, « Verrouiller ces rails ensemble », « Défaire le groupe », Origine) ; glisser un rail : aimant (11 px) sur le circuit et les voies ; clic sur une position dessinée (tirets) : la renommer par un nom proposé, la redéplacer, la supprimer ; glisser une position : la redéplacer. Tag « non connecté : <nom> » pour une position sans voie en face. Aucune valeur à saisir ; jamais envoyé vers OSM (règles : `docs/ref/editeur.md`).
- **Hauteurs du circuit** (montagnes russes, osmrides#53 lot 2, `GAME.profile`) : graphique hauteur (m, au-dessus de la gare ; négative sous le sol) selon l'abscisse `s` du tracé d'origine, avec les repères (gare, lift, freins de bloc et final, tunnels, inversions). « Régler les hauteurs » crée un profil de départ qui suit la courbe d'origine (écart de 0,4 m environ) ; clic sur la courbe : ajoute un point ; glisser un point ou saisir `s` et la hauteur ; case « segment droit jusqu'au point suivant » (`lin`) ; supprimer ; « Origine » retire `GAME.profile`. Le moteur applique le profil (règle unique : `docs/ref/voie.md`) ; un **tunnel enterré** (par exemple sous l'eau, OzIris) se règle en descendant les points sous 0 m, car OSM (`layer=-1`) ne donne pas de mètres. Alertes : pente de plus de 100 % (ESTIMÉ) et circuit infaisable (estimation du moteur, `faisabilite()`). **Couleurs de la voie** : champs de la section « Attraction » (`track` / `trough`), jamais renvoyées vers OSM.
- **Lieu** (section du même nom, osmrides#53) : **horaires d'ouverture et de fermeture du lieu**, communs à **toutes** les attractions du lieu (message d'avertissement dans la section). Écrits dans `lieux/<type>/<lieu>/lieu.js` (`const LIEU = {"hours":{"open":"10:00","close":"19:00"}}`), fichier facultatif lu par `engine/moteur.js` (absent = 10:00 à 19:00), par le bouton **Enregistrer les horaires du lieu** de la section (distinct de l'enregistrement de `game.js` ; `PUT /api/lieu/<type>/<lieu>`). Ouverture de 2 h au moins (ESTIMÉ). Le jeu publié charge `lieu.js` s'il existe : sur un dépôt de jeu, les outils de test qui comptent les erreurs de la console doivent tolérer son absence (comme `game.js`).
- **Apparence de la file et du quai** (section du même nom, issue #45) : sol de la file (une seule section « Sol de la file », « Tous » par défaut, un chemin au choix ou clic sur la carte ; issue #55) : texture et couleur du sol des allées de file (béton d'origine, asphalte, sable stabilisé, pavés, platelage bois) et du sol des quais (béton lissé d'origine ou une des textures), matériau des garde-corps et clôtures de file (métal d'origine, bois, pierre en muret ; les vantaux des barrières pivotantes suivent : bois, ou fer sombre entre piliers de pierre), couleur des portillons du quai (état lu à l'angle et au voyant vert / rouge du poteau). Appliqué à chaud dans le jeu en cadre ; bouton **Origine** par champ. Teintes ESTIMÉES.
- **Envoyer vers OSM** (issue #46, D12) : bouton en haut. Liste les écarts entre les réglages du jeu et les attributs lus dans OSM (`OSM.attrs` : surface / couleur des allées de file, sol du quai, matériau des garde-corps, couleur du toit de la gare ; la couleur de la voie n'est plus renvoyée, décision du propriétaire 24/11) : objet, version importée, clé, ancienne → nouvelle valeur, à cocher ; la création d'un polygone de sol de quai (depuis le quai calculé par le jeu) est proposée, décochée par défaut. Commentaire du changeset modifiable. Jamais automatique. Dans chaque réglage de l'apparence, « OSM » = valeur lue dans OSM, « modifié » = écart avec OSM. Procédure de branchement du compte : section « Envoyer vers OSM » ci-dessous.
- **Réimporter depuis OSM** (osmrides#54, #57 point 7) : bouton en haut. Cocher les catégories à reprendre d'OSM (toutes par défaut), **Télécharger depuis OSM** : le navigateur télécharge la zone de la fiche d'import `tools/specs/<el>.json` du dépôt de jeu, l'éditeur montre les écarts par catégorie (+ ajouté, - retiré, ~ modifié) et les avertissements (circuit ouvert…) ; décocher une catégorie refait l'aperçu sans retélécharger. **Écrire** remplace `lieux/<type>/<lieu>/<el>.data.js` (catégories non cochées gardées telles quelles), puis le jeu se recharge (nombre de points de voie et d'objets affiché). Règles : `docs/ref/import-osm.md`.
- **Différences et enregistrement** : résumé avant / après, diff ligne à ligne du fichier, validation par le serveur, puis **Enregistrer**. **Recharger** abandonne les modifications.

## Format écrit

`lieux/<type>/<lieu>/<el>.game.js` = un en-tête de commentaires puis `const GAME = { … };` dont le corps est du **JSON strict** (D1). Chargé par `jeu.html` après `lieux/parc/asterix/<el>.js` (absent : ignoré) et inclus par `tools/build.py` s'il existe. Priorité : `GAME` > `SITE` > calcul du moteur.

```js
const GAME = {
  "barriers": { "b1": { "x": 7.02, "z": 53.33, "ang": -90.4, "len": 3.44 } },
  "controlRooms": [ { "id": "poste", "x": 2.25, "z": 8.6, "angle": 90, "w": 2.06, "d": 0.94, "main": true } ],
  "boardAreas": [ { "id": "quai", "pts": [ [-1.2, 3.4], [9.8, 3.4], [9.8, 6.1], [-1.2, 6.1] ] } ],
  "board": { "depth": 2.6 },
  "site": { "trains": [ { "name": "Train 1", "col": "#2c4f8c", "col2": "#cfd3da", "wear": 26 } ], "phys": { "drag": 0.0012 } }
};
```

- `barriers` : clé `b<n>` → `{x, z, ang, len, open?, sw?}` (pivot en m, angle en degrés de la position fermée, longueur 0,2 à 20 m, `open: true` = ouverte au début de la partie, `sw: -1` = ouverture dans l'autre sens). Anciennes clés (`entry`, `fork:…`, `add:…`) acceptées avec un avertissement, converties par le jeu, réécrites à la première modification d'une barrière.
- `boardAreas` : 0 ou 1 polygone `{id, pts:[[x, z], …]}` (3 à 64 sommets, en m, bords qui ne se croisent pas, 0,5 m² au moins) ; absent ou `[]` = zone calculée par le jeu.
- `board` : `{depth}` = profondeur des travées d'attente derrière les portillons (m, de 0,5 à 6, et au plus ce que le quai permet : profondeur du quai - 0,5 m - distance des portillons, 1,7 m pour Goudurix, quai de 3,9 m ; le jeu garde au moins un rang) ; absent = calcul du jeu. Priorité `GAME` > `SITE.plat.depth` > calcul.
- `queueEntry` : `{len, ang}` = entrée de la file, segment droit depuis le début du chemin de file OSM (longueur 0 à 30 m, orientation -360 à 360 degrés, 0 = est, 90 = sud) ; absent = calcul du jeu. Priorité `GAME` > `SITE.queue` (`mouth`, `mouthMax`, `link`) > calcul ; `SITE.queue.gateAtMouth` s'applique ensuite.
- `site` : surcharges partielles de `SITE`, clés autorisées seulement : `kind`, `car` (`len` 0,5 à 6 m, `n` 1 à 30, `seats` et `abreast` 1 à 8, `restraint` `lapbar` | `otsr` | `belt` ; `len` x `n` au plus 40 m), `trains` (liste complète de 1 à 8 : `name`, `col`, `col2` en `#rrggbb`, `wear` 0 à 100, `lane` 1 à 8 facultatif), `track` (`spine`, `rail`, `support` en `#rrggbb`), `trough` (`lo`, `hi` en `[r, g, b]`, `edge`, `deck`, `rim` en `#rrggbb`, `shine` en `rgba(…)`), `phys` (`roll` 0 à 0,3 ; `drag` 0 à 0,01 ; `vmin` 1 à 6). Fusion dans `SITE` au début de `engine/core.js` (objets en profondeur, tableaux remplacés) ; toute autre clé est refusée par la validation. Bornes ESTIMÉES. Ajouts de 0.3.0 : `goal` (entier 10 à 20000), `cams` ({id: {label, x, z, s}}, 16 au plus, `s` 2 à 60), `text` ({storm, great}, 160 caractères), `strike` ({area [x min, x max, z min, z max], spot [x, z]}), `jobsites` ({travail: [x, z]}), `lap` (30 à 600 s), `stopBack` (0 à 15 m), `maxRun` (1 à 8), `dropAfter` (0 à 300 m), `loadSide` (1 ou -1), `holdBack` et `preBrake` (tolérés en lecture, ignorés, plus écrits depuis #57 point 4), `zones` ({B<k>: {trim {v 1 à 30 m/s}, launch 1 à 30 m/s, hold 0 à 300 s, stop booléen}}), `yard` ({move {v 0,2 à 10, vc 0,1 à 5, t 0,5 à 30}, devName, devLabel, rails {circuit|garage: {pos [{name, d -40 à 40 m}], 1 à 12} ou {lock}} ; post, laneGap, retract, laneD de 0.6.0 tolérés et ignorés}), `plat` ({load 1,5 à 30, exit 0 à 30, back 0 à 10, front 0 à 10 m}), `car` en plus : `w` 0,5 à 3 m, `inline` booléen, `pitch` 0,2 à 3 m. Toutes ces bornes sont ESTIMÉES (sûres pour le moteur).
- `profile` (osmrides#53 lot 2) : `[[s, hauteur(, "lin")], …]`, 2 à 60 points, `s` de 0 à la longueur du circuit d'origine (au moins 1 m d'écart), hauteur de -15 à 80 m (ESTIMÉES) ; pente de plus de 100 % et circuit infaisable : avertissements. Absent = hauteurs d'origine.
- `look` (issue #45, D11) : `{queue:{col, tex}, plat:{col, tex}, rail, gate, roof}` (`roof` = couleur `#rrggbb` du toit de la gare, issue #46), chaque clé facultative ; `col`, `gate` = couleur `#rrggbb` ; `tex` = `concrete` | `asphalt` | `sand` | `pavers` | `deck` ; `rail` = `metal` | `wood` | `stone` ; absent = rendu d'origine.
- `controlRooms` : 0 ou 1 salle `{id, x, z, angle (degrés), w, d (m), main}` ; `[]` = aucune salle ; clés facultatives `beacon` et `label` = `[x, z]` en m dans le repère de la salle (gyrophare, borné à la salle +/- 0,5 m ; étiquette du pupitre), gyrophare (carré orange) et étiquette (croix) glissés sur la carte quand la salle est choisie, priorité `GAME` > `SITE.beacon` / `SITE.boothLabel` > défaut (ni pupitre dessiné, ni gyrophare, ni étiquette).
- Clés inconnues de l'éditeur (lots futurs) : conservées telles quelles, signalées.

## Envoyer vers OSM (compte du propriétaire)

Connexion OAuth2 avec PKCE, envoi direct depuis l'éditeur local (aucun mot de passe ne passe par l'éditeur ; le jeton reste en mémoire du serveur, jamais écrit ni commité : se reconnecter après un redémarrage).

1. Sur openstreetmap.org, compte connecté : **Mon profil > Paramètres > Applications OAuth 2 > Enregistrer une nouvelle application**. Nom libre (« OSMrides editor »), **URI de redirection** `http://127.0.0.1:8787/osm/callback`, **application confidentielle : non** (client public, PKCE), permission **Modifier la carte** (`write_api`). Copier l'**identifiant client** (pas de secret).
2. Copier `editor/osm.local.example.json` d'osmrides en `osm.local.json` à la racine du dépôt de jeu (chemin lu par `compose.yaml` : `OSM_CONFIG`), y coller l'identifiant client (`clientId`). Le fichier doit être ignoré par git (`.gitignore` du dépôt de jeu) ; il n'est jamais servi par l'éditeur. `api` : serveur d'API (défaut `https://api.openstreetmap.org`) ; `auth` : serveur OAuth (défaut `https://www.openstreetmap.org`). **Pour essayer sans toucher à la vraie carte**, enregistrer l'application sur le serveur de développement OSM (`https://master.apis.dev.openstreetmap.org`, compte à créer là-bas) et mettre ce site dans `api` et `auth` (et `web`).
3. `docker compose up -d` (le fichier est lu à chaque demande, pas de reconstruction) ; ouvrir http://127.0.0.1:8787/ (pas `localhost` : l'adresse doit être celle de l'URI de redirection).
4. Dans l'éditeur : **Envoyer vers OSM > Se connecter à OSM** (fenêtre OSM, autoriser), cocher les écarts, relire le commentaire, **Envoyer**. Le serveur relit chaque objet, refuse si sa version a changé depuis l'import (relancer alors `tools/make_site.py`), ouvre un changeset (`created_by=OSMrides editor`), envoie, le ferme et donne son numéro.
5. Après un envoi : relancer l'import (`osmrides_parks/docs/NOUVELLE-ATTRACTION.md` §4) pour relire les nouvelles versions ; les écarts disparaissent alors.

Les valeurs envoyées sont contrôlées (liste blanche : `surface`, `colour`, `material`, `roof:colour`, et pour un polygone de quai `area:highway=footway`, `covered=yes`, `level=0`) ; rien d'autre ne peut partir.

## Sécurité

- Port publié sur `127.0.0.1` seulement ; le serveur refuse tout autre en-tête `Host` (rebinding DNS) et les écritures d'une autre origine ou non JSON.
- Conteneur : utilisateur non root (`T2Z_UID:T2Z_GID`), système de fichiers en lecture seule (`/tmp` en tmpfs), `cap_drop: ALL`, `no-new-privileges`, pas de socket Docker. Dépôt monté **en lecture seule**, sauf `lieux/`.
- Le serveur sert le dépôt en lecture (GET), sans fichiers cachés (`.git`…) ni traversée de chemin, et n'écrit que `lieux/<type>/<lieu>/<el>.game.js` pour un `<el>` dont `lieux/parc/asterix/<el>.js` existe, après validation (types, bornes, clés connues, 1 salle au plus ; `editor/schema.js`), par écriture atomique ; au réimport OSM, sur le bouton « Écrire » seulement, `lieux/<type>/<lieu>/<el>.data.js` (téléchargement fait par le navigateur). Aucune opération Git, aucun accès réseau sortant du serveur (hors envoi vers OSM).

## Flux Git → Pages

1. Éditer, voir les différences, enregistrer (fichier écrit sur l'hôte).
2. Vérifier dans le jeu : ouvrir `jeu.html?type=parc&lieu=asterix&el=<el>` (fichier local) ; tests : `node tools/check.js <site>` du dépôt de jeu.
